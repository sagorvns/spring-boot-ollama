## 🧠 1. Problem Statement

Design an **Online Turn-Based Game** system (like Chess or Ludo) that:

* Supports real-time multiplayer gameplay
* Manages turns and player moves
* Validates moves and game rules
* Supports matchmaking (random/friends)
* Ensures consistency & cheat prevention
* Persists game state and history
* Sends real-time updates via WebSockets

---

## ✅ 2. Functional & Non-Functional Requirements

### 🔹 Functional Requirements:

* Create/Join game (public/private)
* Matchmaking (auto or invite friend)
* Turn-based gameplay logic
* Real-time move updates to all players
* Chat between players (optional)
* Game result & leaderboard

### 🔹 Non-Functional Requirements:

* Real-time performance (low latency)
* High availability
* Fairness & anti-cheating mechanisms
* Scalability for concurrent games
* Game persistence (resume after disconnect)

---

## 📦 4. Key Components Explained

| Component                 | Description                                               |
| ------------------------- | --------------------------------------------------------- |
| **WebSocket Gateway**     | Real-time communication channel between client and server |
| **Matchmaking Service**   | Pairs players based on skill, type, or friend invite      |
| **Game Session Manager**  | Tracks active games, player turns, timeouts               |
| **Game Logic Engine**     | Validates game-specific rules (e.g., valid Chess move)    |
| **Game State Store**      | Stores state (moves, turn, timer, etc.) per session       |
| **Analytics/Leaderboard** | Tracks scores, history, player stats                      |

---

## 🔄 5. Game State Flow Diagram

```
1. Player A joins a game → Matchmaking pairs Player B
2. Game Session Created → Initial game state saved
3. Player A makes move → Move sent via WebSocket
4. Game Logic validates → Updates Redis/MongoDB
5. Player B notified → Next turn allowed
6. Repeat until game ends → Save result, update stats
```

## 🚦 7. Tech Stack Recommendations

| Feature            | Tech                                |
| ------------------ | ----------------------------------- |
| Realtime           | WebSocket over STOMP/SockJS         |
| Backend            | Java (Spring Boot + WebFlux), Netty |
| Game Rules         | Separate module (Strategy Pattern)  |
| Session Store      | Redis (in-memory, fast)             |
| DB for Persistence | MongoDB or PostgreSQL               |
| Queue (for events) | Kafka or RabbitMQ                   |
| Matchmaking        | Redis Sorted Sets / Queue           |
| Load Balancer      | NGINX or AWS ALB                    |
| Deploy             | Kubernetes, Docker, Helm            |

## 🧠 8. How to Handle...

### 🎮 **Matchmaking**

* Use Redis Sorted Sets (by rating/time) or FIFO queues
* Friend invite → create session with both player IDs

---

### 🧠 **Turn Logic & Move Validation**

* GameEngine validates move before accepting
* Enforce turn-based lock → Redis lock or server check
* Use **server-authoritative model**: never trust client

---

### 🛑 **Cheating Prevention**

* All moves validated on server
* Replay verification by clients for transparency
* Store full move history → for audit or dispute

---

### 🔁 **Disconnections**

* Mark player `DISCONNECTED` in session
* Give `N` seconds to reconnect
* Use sticky sessions or session replication

---

### 🧊 **State Persistence**

* Redis → for fast access
* Mongo/PostgreSQL → for storing completed games, history, leaderboard

## 📚 9. Sample Cross-Questions (With Answers)

---

### ❓ How do you ensure correct turn execution?

✅ Game Session tracks current turn. Each move is checked server-side. If not your turn → reject.

---

### ❓ What if two players try to move at the same time?

✅ Use locking or atomic check-update in Redis (`SETNX` or Lua script) to enforce turn order.

---

### ❓ How would you handle reconnection?

✅ Persist session ID on client → if reconnects within N seconds, resume session; else declare timeout/loss.

---

### ❓ How does matchmaking work?

✅ Either friend invite (direct) or queue-based matchmaking (e.g., skill-based buckets).

---

### ❓ Why use WebSocket and not HTTP?

✅ For real-time, bi-directional, low-latency updates. HTTP is stateless, WebSocket maintains persistent connection.

---

### ❓ How to scale to 1 million concurrent players?

✅ Horizontally scale WebSocket servers, use consistent hashing to route to correct game session. Use Redis for shared state.

---

### ❓ How is game history stored?

✅ Store compact JSON with timestamped move list. E.g.:

```json
{ "moves": [ "A1→B2", "B2→C3" ], "winner": "Player1" }
```

---

### ❓ How do you prevent duplicate moves?

✅ Use Redis `SETNX` per turn ID. Each turn ID is unique and atomic.
