## ✅ 1. Problem Statement

**Design a social media platform** where users can:

* Register/Login
* Post text/images/videos
* Follow/unfollow other users
* View a feed (timeline) of posts
* Like, comment, share
* Search users or hashtags
* Get real-time notifications

---

## ✅ 3. Core Services Breakdown

### 🔐 **User Service**

* Register, login, update profile
* OAuth, JWT
* DB: PostgreSQL

---

### 📸 **Post Service**

* Handles creation/edit of posts (text, image, video)
* Uploads media to **S3-compatible object storage**
* Stores metadata in PostgreSQL

---

### 🧾 **Feed Service**

* Timeline generation for each user
* Two approaches:

  * **Push model**: On post, fan-out to followers' feeds (used by Facebook)
  * **Pull model**: Fetch posts from followed users on demand (used by Twitter)
* Stores in **Redis** (fast retrieval) or **Cassandra**

---

### ❤️ **Like/Comment Service**

* Store likes/comments for each post
* High write volume, so use **NoSQL like Cassandra**
* Enable pagination for comments

---

### 🔔 **Notification Service**

* Triggered via Kafka when post is liked, user followed, comment added
* Stores unread notifications in Redis/DB

---

### 🔎 **Search Service**

* User or hashtag search
* Full-text index using **Elasticsearch**

---

### 👥 **Follow Service**

* Store mappings:

  * `user_id -> list_of_followers`
  * `user_id -> list_of_following`
* Redis for quick lookup + DB for persistence

---

### `Comment`

### `Follow`

\| follower\_id | followee\_id |

---

## ✅ 5. Timeline Generation Strategies

### Push Model (Fan-out on write):

* When a user posts, push the post ID to all followers’ feeds
* Fast reads, slow writes
* Ideal for active readers (like Facebook)

### Pull Model (Fan-out on read):

* Fetch latest N posts of followees on request
* Slow reads, fast writes
* Good for low-follower users (like Twitter)

---

## ✅ 6. Real-Time Notifications

Use Kafka for event streaming:

```
[Like] → Kafka → [Notification Service] → [WebSocket / Email / Push]
[Comment] → Kafka → [Notification Service]
```

* Store unread notifications in Redis or NoSQL for quick access
* WebSocket for real-time delivery to client

---

## ✅ 7. Media Storage

* Images/videos stored in **Amazon S3** or **MinIO**
* Store URLs in DB
* Use CDN (CloudFront) to optimize delivery

## ✅ 10. Common Cross-Questions & Answers

### ❓ Q1: How do you ensure feed freshness at scale?

**A:** Use Redis to store recent post IDs per user. Combine Push (active users) + Pull (inactive users) models based on thresholds.

---

### ❓ Q2: What happens if a user has 10M followers?

**A:** Avoid fanning out to all. Instead:

* Fan-out to top-K active users
* Others pull posts on demand

---

### ❓ Q3: How do you handle media uploads?

**A:** Upload media to S3 via signed URLs. Store URL in DB. Use CDN for fast access.

---

### ❓ Q4: How do you scale comments/likes per post?

**A:** Use **Cassandra** with partition key = post\_id. Add pagination support and limit size.

---

### ❓ Q5: How to avoid duplication of notifications?

**A:** Use idempotent Kafka consumers + deduplication logic in the Notification DB.
