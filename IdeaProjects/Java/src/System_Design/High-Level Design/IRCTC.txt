## ✅ 1. Problem Statement

**Design an online ticket booking system (e.g., IRCTC)** that allows users to:

* Search trains by source/destination/date.
* View seat availability.
* Book/cancel tickets (handle concurrency).
* Make payments.
* Get confirmation.
* Admins can add/edit trains.

## ✅ 4. Detailed Service Breakdown

### 4.1 🔐 **User Service**

* Register, login, manage profile
* Tech: Spring Boot, JWT, OAuth2
* DB: PostgreSQL/MySQL

---

### 4.2 🚂 **Train Service**

* CRUD for train routes, schedules
* Search trains by date/location
* Cache frequent routes in Redis
* DB Schema: `Train`, `Route`, `Schedule`

---

### 4.3 📆 **Seat Availability + Booking Service**

* **Most critical part (high concurrency)**
* Use **Redis locks** or **Zookeeper** to prevent overbooking
* Booking flow:

  * Lock seat in Redis (`SETNX`)
  * Confirm payment
  * Persist booking to DB
  * Release lock after timeout (auto)
* Retry/Timeout handled by Redis TTL or retry logic

---

### 4.4 💰 **Payment Service**

* Integrate with Razorpay/Stripe
* Handle success/failure
* Use callback to notify Booking Service
* Save transactions for audit

---

### 4.5 📩 **Notification Service**

* Send email/SMS on booking
* Async using Kafka

---

### 4.6 🧠 **Admin Panel**

* Add/edit trains, seats, pricing

## ✅ 6. Concurrency Handling (Core)

### 📌 Booking Flow:

```
1. User selects train/date/seat
2. API calls BookingService → Redis
3. Redis `SETNX(seat_id, user_id)` locks the seat
4. Timeout: 5 mins TTL
5. Payment success → persist to DB
6. Fail/timeout → unlock seat
```

> Use Redisson library for Redis distributed lock (Java)

## ✅ 9. Cross-Questions & Answers

### ❓Q1. How will you prevent double booking of the same seat?

**A:** Use Redis with `SETNX` to lock the seat during booking. TTL ensures release if payment fails. Redisson simplifies distributed locks in Java.

---

### ❓Q2. What if payment succeeds but Redis lock is gone?

**A:** Use idempotent booking logic. Payment service sends a transaction callback; we re-validate and confirm booking in DB even if Redis lock is expired.

---

### ❓Q3. How do you scale Booking Service?

**A:** Horizontally, because Redis lock ensures coordination. Use DB sharding (per train or date) to avoid write bottlenecks.

---

### ❓Q4. How to handle partial failure after payment?

**A:** Design BookingService to be **idempotent** and use **Saga pattern** or **event-driven rollback** (Kafka + compensation service).

---

### ❓Q5. Why not store seat availability in DB only?

**A:** DB writes under high concurrency will slow down. Redis offers in-memory performance with atomic operations.
