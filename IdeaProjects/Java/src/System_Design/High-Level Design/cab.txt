## 🎯 1. Requirements & Assumptions

### Functional Requirements

* Rider can search and request rides with origin/destination.
* Driver can receive, accept or reject ride requests.
* Real-time driver location tracking and ETA updates.
* Fare estimation, trip creation/completion, and payments.
* Rider and driver ratings post-trip.
* Trip history for both users.

### Non-Functional Requirements

* Low latency matching and updates.
* High availability and fault tolerance.
* Global scalability (city-level and geo-sharding).
* Strong consistency for trip data and eventual consistency for location.
* API security and fraud detection.

### Assumptions

* Java-based microservices (Spring Boot, gRPC/REST).
* WebSocket or push mechanisms for real-time connectivity.
* Kafka for streaming; Redis and NoSQL (Cassandra) & SQL for storage.
* Geospatial indexing using GeoHash or Google S2.

## 🔍 2. High-Level System Architecture

* **User/Driver Apps**: Rider and driver mobile clients.
* **API Gateway & Load Balancer**: Routes WebSocket/HTTP requests, with geo-DNS directing to nearest data center.
* **Auth Service**: OAuth2/JWT token issuance and verification.
* **Demand Service**: Handles ride requests, fetches ETA, interacts with Cab Finder.
* **Supply Service**: Ingests real-time driver location updates.
* **Cab Finder / Dispatch (DISCO)**: Uses geo-index (GeoHash or Google S2) to match riders with drivers.
* **Trip Service**: Manages lifecycle and status of trips.
* **Real-time Location Service / WebSocket Manager**: Maintains active sockets and publishes updates.
* **Data Pipeline (Kafka)**: Queues location updates, ride events, and payment or notification triggers.
* **Databases**:

  * SQL (Postgres/MySQL) for user/driver profiles, trip metadata
  * NoSQL (Cassandra) for driver location time-series and trip archive
  * Redis for fast lookup: current driver availability and geospatial cell membership
* **Payment Service**, **Notification Service**, **Rating Service**

## 📊 3. Component Interaction & Data Flow

In this architecture:

* Drivers send location updates via WebSocket or REST, which is published to Kafka.
* Location Service processes feeds, stores recent location in Redis and Cassandra.
* Rider requests go through Demand Service; Cab Finder queries nearby drivers using geo-index.
* Matching proposals sent via WebSocket Manager or push to driver apps.
* Driver acceptance leads to Trip Service managing booking; event flows to payment and notification services.
* Data pipeline processes events for analytics, dynamic pricing, fraud detection.

## ⚙️ 5. Database & Storage Design

| **Entity**              | **Purpose**                               | **Recommended Store**              |
| ----------------------- | ----------------------------------------- | ---------------------------------- |
| Driver Locations        | Real-time geo tracking                    | Redis (live) + Cassandra (archive) |
| Rider & Driver Profiles | Authentication and metadata               | SQL (e.g., PostgreSQL)             |
| Trip Metadata           | Active ride state management              | SQL                                |
| Trip History            | Completed ride data for analytics & audit | Cassandra                          |
| Ride Matches & ETA      | Fast lookup and caching                   | Redis or in-memory cache           |

Location streams and event flows go into Kafka for async processing and analytics pipelines.

## 🔄 6. Scaling & Availability Strategies

* **Geo-Sharding**: Partition services and data per city or region, minimizing latency and localizing traffic.
  ([Reddit][12])
* **Consistent Hashing / GeoHash / S2**: Spatial indexing to quickly retrieve nearby drivers.
  ([Medium][8])
* **Auto-Scaling**: Dynamic scaling of Demand and Supply services based on RPS and active drivers.
  ([DEV Community][3])
* **High Availability**: Redis cluster replication, multi-AZ Kafka, failover policies.
* **Eventual Consistency**: Acceptable for presence and location; strong consistency for trip and payment data.

## 🧠 7. Interview Cross-Questions & Model Answers

| **Q**                                                                             | **Answer**                                                                                                                                                             |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Why use Redis and Cassandra together?                                             | Redis handles fast real-time lookups (current driver status/location). Cassandra stores durable, high-throughput time-series historical data.                          |
| How do you efficiently match riders and drivers?                                  | GeoHash or S2 indexing groups nearby drivers into spatial cells. Lookups limited to the same or adjacent cells with available drivers.                                 |
| How to handle driver location updates at scale (\~30k/sec)?                       | Use WebSocket streaming → Kafka ingestion → Redis and Cassandra asynchronously. In-memory DriverLocationHT / grid service stores recent records.                       |
| How to avoid race conditions when multiple drivers receive the same trip request? | Use distributed locking per rider-trip (e.g., Zookeeper or optimistic locking) so only one acceptance is committed. Others get notification of rejection.              |
| How to prevent fraud or unreliable users/drivers?                                 | Use ML-based anomaly detection on trip/payment patterns; real-time scoring in Dispatch pipeline; implement verification checks and rate limiting.                      |
| How to calculate ETA and dynamic pricing?                                         | Dispatch uses historical and real-time traffic data; integrate external map APIs. Dynamic pricing uses surge multipliers, demand-supply ratio, and time-based factors. |
| How to support cancellation or no-show?                                           | Trip Service updates status; queue compensating transactions; inform both parties; handle refunds or penalty charges via Payment Service.                              |

## 📝 8. Revision Summary (Cheat-Sheet)

* **Key flows**: Rider → Demand Service → Cab Finder → Schedule trip → WebSocket Manager → Driver acceptance → Trip Service.
* **Location ingestion**: Driver → WebSocket/REST → Kafka → Redis & Cassandra.
* **Matching**: GeoHash or S2 spatial indexing + consistent hashing.
* **Services**: Demand, Supply, Dispatch (Cab Finder), Trip, Payment, Notification.
* **Storage**: Redis for cache, SQL for metadata, Cassandra for historical data.
* **Scalability**: Geo-sharding, auto-scaling, Kafka streaming.
* **Reliability**: Replication, locking, eventual cessation of inconsistent states.
